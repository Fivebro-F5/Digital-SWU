# 项目约束

依据：[项目概述 v1.0](数字西大-项目概述.md)。本文把概述中的已确定内容转为开发与验收规则；未确定事项见[待决策事项](待决策事项.md)。若用户之后明确修改需求，以新要求为准并同步修订文档。

## 1. 产品与阶段范围

项目是 Web 数字校园游戏化平台，目标模块为校园导览、社交互动与校园服务。首期采用核心技术纵向验证，必须交付以下闭环：

1. 微内核、插件注册及基础通信机制。
2. 一个局部校园等距 2.5D 场景。
3. 玩家移动与地点交互。
4. 游客访问、用户注册和登录。
5. Socket.IO 多人同屏和基础状态同步。
6. 场景与 PostGIS 地点数据的坐标映射。

MVP 验收重点是前端、后端、数据库、插件和多人游戏链路贯通。完整地图、空教室、商铺、设施、室内/鸟瞰、聊天、社区、跳蚤市场、校园通知与教务集成属于后续迭代；它们不得成为 MVP 完成的隐含前置条件。

## 2. 技术边界

| 层面 | 已确定选择 | 实施约束 |
|---|---|---|
| Web 前端 | HTML5、Vue 3、TypeScript、Vite | UI 与游戏场景按明确接口协作 |
| 游戏 | Phaser，等距 2.5D | 场景、角色、交互和地图资源分离 |
| 服务端 | NestJS、Node.js、TypeScript | 业务能力通过独立模块/插件实现 |
| 数据 | PostgreSQL、PostGIS、Drizzle ORM + SQL | 空间查询可用 SQL；数据库结构须通过迁移管理 |
| 实时 | Socket.IO | 服务端维护权威状态并验证行为 |
| 缓存 | 内存缓存，预留 Redis | 不把单进程内存当成持久会话或最终业务数据 |
| 文件 | MinIO | 用户上传与地图/代码版本资源分开管理 |
| 地图制作 | Tiled、Phaser Editor | Tiled 管地图、图层、碰撞；Phaser Editor 管场景与交互 |
| 素材 | Tileset、独立建筑素材 | 地形复用 Tileset，标志建筑单独管理 |

不得在无设计记录的情况下用另一套核心框架替换已选技术。库版本、包管理器、代码目录和部署方式尚未确定，应在初始化任务中记录具体选择。

## 3. 架构与数据约束

- 核心仅负责插件注册、生命周期、服务发现、权限接口及异常处理。地图、社交、教务等业务能力独立扩展，禁止把业务规则塞入核心。
- 插件通过类型化服务接口和事件总线协作；明确契约、版本和测试边界。内置插件按需加载，动态加载只预留受控扩展点。
- 地理坐标与游戏坐标分离；使用经校对的地理控制点进行转换，并记录坐标系、控制点和转换版本。地理位置、建筑范围和空间关系存入 PostGIS。
- 校园地理信息由人工采集、校对、制作。未经核实的数据不能表现为准确的导航或实时状态。
- 玩家状态由服务端维护；客户端提供输入、渲染和平滑插值。服务端验证移动与交互，并按场景分区同步必要状态。
- 持久化用户、社交、聊天和业务数据由 PostgreSQL 管理。临时内存状态必须可恢复或可重建；需要跨实例共享时通过抽象切换到 Redis 等方案。

详细边界见[架构与接口约定](../architecture/架构与接口约定.md)。

## 4. 身份、安全与数据接入

- 游客只能使用公开导览和信息查询；注册用户可使用获准的社交和互动能力。所有敏感操作必须在服务端校验身份和权限，使用 RBAC。
- 认证采用混合模式，Session + Cookie；学校统一身份认证只预留接口，未获授权前不宣称已接通。Session 初期存于 PostgreSQL 等可靠持久化存储。
- 生产环境使用 HTTPS、安全 Cookie 和 CSRF 防护；Socket.IO 握手及事件复用服务端身份验证和授权规则。用户输入、上传文件和实时事件均须校验。
- 不收集或代存学校统一认证密码，不绕过认证或抓取无授权数据。教务第一阶段仅提供官方入口与合规数据导入；正式 API 对接需授权，课表和空教室数据只在可合法获取且可靠时集成。
- 校园通知可人工维护或授权同步；后台需支持审核、去重、更新，并记录来源和更新时间。数据缺失或过期时应显式标注，不伪造可用性。
- 用户上传图片及附件存储在 MinIO；权限控制、文件类型和大小限制在实现上传功能时明确。社区内容审核、隐私规则及数据保留周期尚待决策，相关功能上线前必须确定。

## 5. 质量与交付门禁

- 可维护性优先：单一职责、低耦合、标准接口、统一 TypeScript 类型与代码规范。
- 每次提交或合并请求：类型检查、静态检查和快速单元测试。每日：集成与主要流程测试。每周：全量自动化回归。每轮迭代：技术债评估及必要重构。
- 核心模块行覆盖率至少 80%，整体代码行覆盖率至少 70%；关键业务流程全部纳入端到端测试。覆盖率不能替代正确性、安全性和性能验证。
- 权限、异常路径和插件兼容性属于重点测试。类型检查、静态检查和必需测试全部通过后方可合入受保护分支。
- 每个交付任务应说明改动、契约或迁移影响、实际执行的验证、未验证原因和仍待决策事项。没有代码或 CI 时，不得声称质量门禁已通过。

## 6. 变更控制

超出 MVP 的业务功能、替换既定技术、改变身份/地图/插件/实时状态模型，需先记录理由、影响和迁移路径，并更新相关文档。部署、监控、容量、备份、隐私等未决事项不得被写成既定事实。
