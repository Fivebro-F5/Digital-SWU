# 西南大学数字校园游戏

**项目概述 v1.0**

## 1. 项目定位

基于 Web 的西南大学数字校园游戏化平台，融合校园导览、社交互动与校园服务，构建可探索、可交互、可扩展的虚拟校园。

## 2. 功能模块

### 2.1 校园导览

- **校园地图**：地图浏览、地点定位与导航。
- **空教室查询**：教学楼及教室空闲状态查询。
- **校园游览**：室内、室外及全校鸟瞰场景。
- **店铺查询**：校内商铺位置与信息。
- **设施查询**：厕所等公共设施定位。

### 2.2 社交互动

- **交友聊天**：用户交友与即时通信。
- **社交游戏**：多人互动及校园小游戏。
- **校园贴吧**：帖子发布与社区互动。
- **跳蚤市场**：二手商品发布与交易交流。

### 2.3 校园服务

- **校园通知**：学校事项与活动信息。
- **教务接入**：通过合规授权渠道获取教务信息。

## 3. 技术架构

### 3.1 技术栈

| 分类 | 技术 |
|---|---|
| Web 基础 | HTML5 |
| 前端 | Vue 3 + TypeScript + Vite |
| 游戏引擎 | Phaser（2D/2.5D） |
| 后端 | NestJS + Node.js + TypeScript |
| 数据库 | PostgreSQL + PostGIS |
| 数据访问 | Drizzle ORM + SQL |
| 实时通信 | Socket.IO |
| 缓存 | 内存缓存，预留 Redis |
| 文件存储 | MinIO |
| 地图编辑 | Tiled + Phaser Editor |
| 素材组织 | Tileset + 独立建筑素材 |

### 3.2 微内核与插件系统

**原则：最小核心、插件化扩展、低耦合。**

- **核心职责**：插件注册、生命周期、服务发现、权限接口与异常处理。
- **加载机制**：内置插件按需加载，预留受控动态加载。
- **通信机制**：类型化服务接口 + 事件总线。
- **依赖规范**：标准接口契约、版本管理及独立测试。
- **业务扩展**：地图、社交、教务等功能以独立插件实现。

### 3.3 地图与场景

- **数据来源**：校园地理信息由人工采集、校对和制作。
- **场景表现**：Phaser 等距视角 2.5D。
- **地图编辑**：Tiled 负责地图、图层及碰撞；Phaser Editor 负责场景与交互。
- **素材管理**：通用地形使用 Tileset，标志性建筑使用独立素材。
- **坐标体系**：地理坐标与游戏坐标分离，通过地理控制点校准转换。
- **空间存储**：PostGIS 管理位置、建筑范围及空间关系。
- **场景管理**：室内、室外及鸟瞰场景独立组织，支持移动、交互与切换。

### 3.4 用户认证与权限

**混合认证 + Session + Cookie + RBAC**

- 游客可使用公开导览与信息查询。
- 注册用户可访问社交及互动功能。
- 预留学校统一身份认证接口。
- Session 使用可靠持久化存储，初期采用 PostgreSQL。
- 使用 HTTPS、安全 Cookie、CSRF 防护及服务端权限校验。
- Socket.IO 连接复用服务端身份验证与授权机制。

### 3.5 实时通信与多人同步

- **Socket.IO**：即时聊天、房间通信、事件推送与断线重连。
- **服务端权威**：服务器维护玩家状态并校验行为。
- **场景分区**：仅向相关场景玩家同步必要状态。
- **客户端**：负责输入采集、渲染与平滑插值。

### 3.6 数据与存储

- **PostgreSQL**：持久化用户、社交、聊天及业务数据。
- **PostGIS**：管理地理空间数据。
- **Drizzle ORM + SQL**：类型化数据访问、数据库迁移及空间查询。
- **内存缓存**：保存临时状态，预留 Redis 适配接口。
- **MinIO**：保存用户上传的图片及附件。
- **资源管理**：地图工程、游戏素材和代码纳入版本管理。

## 4. 校园数据接入

### 4.1 校园通知

- 人工维护与授权自动同步相结合。
- 管理后台提供审核、去重及更新功能。
- 记录信息来源与更新时间。

### 4.2 教务系统

- **第一阶段**：官方系统入口与合规数据导入。
- **第二阶段**：经授权对接正式 API。
- **第三阶段**：逐步集成课表、空教室等可获取数据。

不收集或代存学校统一认证密码，未获得可靠数据的功能标记为暂不可用。

## 5. MVP 开发范围

**策略：核心技术纵向验证。**

首期完成：

1. 微内核、插件注册与基础通信机制。
2. 一个局部校园等距 2.5D 场景。
3. 玩家角色移动及地点交互。
4. 游客访问、用户注册与登录。
5. Socket.IO 多人同屏及基础状态同步。
6. 场景与 PostGIS 地点数据的坐标映射。

**验收目标**：打通前端、后端、数据库、插件和多人游戏的完整技术链路。其他业务模块在后续迭代逐步实现。

## 6. 开发与质量保障

### 6.1 核心原则

- 可维护性为最高优先级。
- 模块单一职责、低耦合、接口标准化。
- 统一 TypeScript 类型与代码规范。
- 通过自动化检查、代码审查及持续重构控制技术债。

### 6.2 测试周期

| 触发条件 | 测试内容 |
|---|---|
| 每次提交 / 合并请求 | 类型检查、静态检查、快速单元测试 |
| 每日 | 集成测试及主要业务流程测试 |
| 每周 | 全量自动化回归测试 |
| 每轮迭代 | 技术债评估及必要重构 |

### 6.3 量化质量门禁

- **核心模块行覆盖率 ≥80%**。
- **整体代码行覆盖率 ≥70%**。
- 关键业务流程全部纳入端到端测试。
- 类型检查、静态检查及必需测试全部通过。
- 重点检查权限、异常路径及插件兼容性。
- 未通过质量门禁的代码不得合入受保护分支。
- 每轮迭代评估技术债并安排必要重构。

覆盖率仅是基础指标，不替代行为正确性、安全性和性能测试。
